## 排障：首次 tag 推送没触发 workflow
- 现象：首次 `git push origin main v0.1.0`（分支+tag 同一条命令）没触发，但工作流文件正常、state=active。
- 真正根因：**branch 与 tag 在同一次 push 里送出时，tag 触发的 workflow 偶发不派发**（GitHub 已知行为），与仓库 Actions 设置无关。
- 修正方式：删除远端 tag 再单独重推（`git push origin :v0.1.0` + `git push origin v0.1.0`）即触发 Run #1。用户明确未改动任何 repo Settings（我之前误判为 Actions 被禁用，已纠正——那步是多余动作）。
- 教训：发版时**分开推更稳**——先 `git push`（分支），再 `git push origin <tag>`；别把 tag 和分支塞进同一条 push。若再遇「没跑」，先单独重推一次 tag，而不是去怀疑 Settings。

## 排查并修复 MCP content union 兼容隐患（源于 media-mcp 同类 bug）
- 触发：media-mcp 发现新版 SDK 客户端在 schema 校验阶段抛 invalid_union，成功响应体被整个丢弃。
  排查本项目是否有同类隐患。
- **根因（通用，值得记住）**：MCP `ContentBlock` union = `text | image | audio | resource_link | resource`。
  其中 `EmbeddedResource.resource` 的类型是 `TextResourceContents | BlobResourceContents`，
  即**必须是 `{uri, text}` 或 `{uri, blob}`**；只给 `{uri, mimeType}` 两个分支都不匹配 → 整条 result 被客户端拒收。
  `resource_link` 则要求 `uri` **和 `name`**（name 来自 BaseMetadata，必填，容易漏）。
  注意这**不是新规范的破坏性变更**——2024-11-05 起要求就是如此，只是旧客户端不做严格校验，新 SDK 才开始拒收。
- 本项目排查结论：`internal/mcp/tool.go` 的 `ResourceContent(uri, mimeType)` 有**完全相同的缺陷**，
  但它是**死代码**——全仓库无调用点（三个工具只发 `text`，server.go 空结果兜底也是 `text`），
  所以线上无实际故障，属埋雷。`ImageContent` 合规（base64 + mimeType），保留。
- 处理：**直接删除 `ResourceContent`**，而非改成 `resource_link`。理由——本项目未实现 resources capability，
  不提供任何可被引用的 resource，返回资源引用在架构上就不成立；按 YAGNI 删掉比留个没人用的正确 helper 更干净。
- 防回归：新增 `internal/mcp/tool_test.go`，内含按 spec 实现的 `validContentBlock` 校验器 +
  三个测试（builder 合规性表驱动、ImageContent base64 往返、裸 `{uri,mimeType}` resource 必须判非法）。
- 验证：`go vet` + 全量 `go test` 通过；`make all` 四端重新编译（11~12MB）；
  `--check` 退出 0（3 tools registered）。**因删的是死代码，运行时行为零变化，无需在 WorkBuddy 重新「信任」连接器**
  （这点与 media-mcp 不同，那边是真实 bug 必须换 exe）。
- 遗留：`bin/llm-eyes-mcp.exe~` 是 Go linker 在 .exe 被运行中进程占用时留下的备份，删不掉（文件锁）。
  已被 `.gitignore` 的 `/bin/` 与 `*~` 双重覆盖，无害，下次构建会自然替换。
- 未触碰：协议版本仍是 `2024-11-05`。升级到 2026-07-28 是 `docs/mcp-跟进评估.md` 里已评估并**主动推迟**的独立事项，
  与本次 content union 修复无关，不要混为一谈。
- 已核对最新 `2026-07-28` schema：`ContentBlock` union **与 2025-06-18 完全一致**（text/image/audio/resource_link/resource），
  无 `image-uri` 之类变体，`ImageContent` 仍是 base64 内联。**即将来迁到 2026-07-28 时 content 层无需改动**，
  迁移面仍只在握手层。`ResourceLink` 必填三项：`type` + `name`(BaseMetadata) + `uri`(Resource)。

## 上一轮审计的自审补正（2026-08-05 晚）
- **L3 修复本身成立**：L3 是内存 LRU（`NewL3`/`container/list`），不落盘，改 key 格式无迁移问题；L1/L2 key 未动。
- **漏报的行为变更**：`providerFor` 现在排在 L3 命中检查之前——之前 `provider:"不存在"` + L3 命中会静默返回缓存；现在会 fail-fast
  报错。语义更对，但属未披露的变更。
- **漏报的真 bug（比千分值那条更根本）**：`detectObjects` 把 **原始** `img.Width/Height` 喂给 `parseDetections`/`normaliseCoords`，
  但模型看到的是 **缩放后**（≤1500px）的 `proc.Data`。后果：
  - 归一化[0,1]回复：不受影响（maxV≤1.5 直接返回）——这是默认/期望路径，故爆炸半径有限；
  - **像素回复**：像素是相对模型看到的缩放图，却除以原始尺寸 → 任何被缩放的图（长边>1500px）坐标全错。**上一轮漏了**；
  - 千分值：÷1000 与尺寸无关，但 pixels-vs-thousandths *判定* 用了原始尺寸 → 大图误判（上一轮已报）。
  根因统一：`normaliseCoords` 应吃**缩放后**尺寸（`proc.Width/Height`），而非原始。修法：fresh 路径直接传 `proc.Width/Height`；
  L2 命中路径无 `proc`，需把 `imgproc.targetSize` 导出为纯函数按 `img.Width/Height + HardOptions()` 重算（HardMaxEdge 是常量、确定）。
  千分值大图歧义即便修了仍残留（缩放图仍可能 1000–1500px），需带外 `coord_convention` 才能彻底解。**待用户拍板是否修。**

## 像素路径尺寸错配 bug 已修（2026-08-05 晚，最不会留技术债方案）
- **根因**：`detectObjects` 把**原始** `img.Width/Height` 喂给 `parseDetections`/`normaliseCoords`，但模型看到的是
  `proc.Data`（缩放后 ≤1500px）。像素回复被原始尺寸除 → 任何被缩放的图（长边>1500px）坐标全错。
- **修法（自描述信封，零耦合）**：
  - `measure.go` 新增 `measureCacheEntry{Text,W,H}`；L2 存的是 `{text,w,h}` 信封而非裸文本，命中重解析时用信封里记的
    「模型看到的尺寸」，不再依赖 `HardMaxEdge` 是常量——将来改 sizing 也不会误解析旧条目（旧裸文本条目自然解析失败被丢弃）。
  - fresh 路径 `parseDetections(resp.Text, proc.Width, proc.Height)`；`lastMissing` 签名改为 `(labels, reply, w, h)`，传 `proc` 尺寸。
  - `parse.go` 收紧 `normaliseCoords`/`parseDetections` 注释，写明 imgW/imgH 必须是模型看到的尺寸 + 残留千分值歧义。
- **测试**：`parse_test.go` 加 `pixels relative to resized image` 用例；`measure_test.go` 加
  `TestMeasureImageL2HitAcrossMeasureTypes`（L2 信封跨 measureType 往返）+ `TestMeasureImagePixelsRelativeToResizedImage`
  （2000x1333→缩放 1500x1000，mock 吐相对缩放图的像素，断言距离=1600.00 而非 bug 的 1200.00）。
- `go vet`/全包 `go test` 全绿；`make all` 四端重编译；`--check` 退出 0。
- **残留（已知限制，非债）**：千分值在缩放图长边 ≥1000px 时仍与像素歧义，需带外 `coord_convention` 才能彻底解——未实现，注释已写明。
