# MCP 2026-07-28 新协议总结与迁移开发指南


## 一、协议更新概述

2026年7月28日，Model Context Protocol（MCP）发布了自2024年11月诞生以来**最大规模的架构重构**。MCP工程负责人Mazin Gilbert直言：“有状态Session是企业从试点走向数万Agent规模部署的首要障碍。”这次更新将协议核心从**有状态的双向协议彻底改造为无状态的请求/响应协议**。

核心维护者David Soria Parra表示：“有人开玩笑称之为v2，我认为在精神上这是准确的——这可能是我们对协议做过的最大改动。”这次更新由Linux基金会旗下的Agentic AI Foundation（AAIF）主导发布。

> **注意**：用户问题中日期写为“202-07-28”，应为**2026年7月28日**。

### 核心变更一览

| 变更项 | 旧版（2025-11-25及以前） | 新版（2026-07-28） |
|--------|------------------------|-------------------|
| 会话管理 | 协议层维护Session，需Mcp-Session-Id | **完全移除**，每次请求自包含 |
| 握手流程 | initialize/initialized握手 | **完全移除** |
| 协议版本与能力 | 握手时协商 | 在`_meta`中逐请求携带 |
| 服务发现 | 隐含在握手中 | 新增**server/discover** RPC |
| 服务端主动请求 | roots/list、sampling等 | 替换为**MRTR**（多轮往返请求） |
| 列表结果 | 因会话而异 | **可缓存**，不因连接变化 |
| 订阅机制 | resources/subscribe等 | 替换为**subscriptions/listen** |
| 日志级别 | logging/setLevel独立请求 | 在`_meta`中逐请求设置 |
| Tasks | 核心协议内 | 移至**官方扩展**（io.modelcontextprotocol/tasks） |
| 废弃功能 | — | Roots、Sampling、Logging、HTTP+SSE |


## 二、关键新特性详解

### 2.1 无状态核心（Stateless Core）

这是本次更新最核心的变化。旧版MCP要求客户端与服务器维持长连接会话——这在单机调试时毫无问题，但搬进生产环境后，Pod一重启整个会话就会丢失；负载均衡被迫做粘性路由；Kubernetes的水平扩缩容形同虚设。

新版中，每个请求都自带完整的协议版本、客户端能力和身份标识（通过`_meta`字段）。远程MCP服务器可以像普通HTTP服务一样部署在标准负载均衡器后面。

### 2.2 server/discover RPC

服务器**必须**实现此RPC来公布支持的协议版本、能力和身份标识。客户端可以在任何其他请求之前调用它进行版本选择，或用作向后兼容性探测。

### 2.3 多轮往返请求（MRTR）

旧协议中服务端可以主动请求客户端（如要求用户确认删除），这依赖持续连接。新版用MRTR模式替代：服务器返回`InputRequiredResult`（resultType: "input_required"），其中包含需要额外信息的请求列表；客户端在重试原请求时附带`inputResponses`提供所需信息。这使得交互式工具不再需要长期存活的会话。

### 2.4 正式废弃政策

建立了**至少12个月**的正式废弃期——从功能正式标记为废弃到实际移除之间至少有12个月时间，安全紧急更新除外。

### 2.5 官方扩展框架

Tasks、MCP Apps等功能从核心协议移至官方扩展。


## 三、迁移开发指南

### 3.1 服务端迁移

#### 步骤一：升级SDK依赖

各一级SDK均已发布支持2026-07-28规范的版本：

| SDK | 版本 | 状态 |
|-----|------|------|
| Python | v2.0.0 | 7月28日同步发布稳定版 |
| TypeScript | v2.0.0 | 7月28日同步发布稳定版 |
| Go | v1.7.0 | 支持2026-07-28协议 |
| C# | v2.0.0 | 预览版已发布 |

**Python示例**：
```python
# 旧版 v1
from mcp.server.fastmcp import FastMCP
mcp = FastMCP("Demo")

# 新版 v2
from mcp.server import MCPServer  # FastMCP已重命名
mcp = MCPServer("Demo")
```


#### 步骤二：移除握手逻辑

删除所有`initialize`/`notifications/initialized`握手代码。新版中协议版本和能力通过`_meta`字段逐请求传递。

#### 步骤三：移除会话管理

删除所有`Mcp-Session-Id`相关逻辑。跨调用状态改为通过**显式业务句柄**在工具参数中传递：

```python
# 旧版：依赖会话保持状态
# 新版：显式传递句柄
第一次调用: create_browser() → 返回 browser_id
后续调用: open_page(browser_id) → click(browser_id) → screenshot(browser_id)
```


#### 步骤四：实现 server/discover

服务器必须实现此RPC来公布支持的协议版本和能力。

#### 步骤五：适配MRTR

将旧的`roots/list`、`sampling/createMessage`、`elicitation/create`等服务端主动请求替换为MRTR模式——返回`InputRequiredResult`，让客户端在重试时提供所需信息。

#### 步骤六：处理废弃功能

以下功能已被废弃但享有12个月兼容窗口：
- Roots
- Sampling
- Logging
- HTTP+SSE（已被Streamable HTTP替代）

#### 步骤七：更新订阅机制

将`resources/subscribe`/`resources/unsubscribe`替换为`subscriptions/listen`。

### 3.2 客户端迁移

#### 步骤一：升级SDK到对应v2版本

#### 步骤二：移除初始化握手

删除`initialize`调用和`initialized`等待逻辑。客户端应在每个请求的`_meta`中携带：
- `io.modelcontextprotocol/protocolVersion`
- `io.modelcontextprotocol/clientCapabilities`
- `io.modelcontextprotocol/clientInfo`（推荐）

#### 步骤三：适配版本不匹配处理

当服务器返回`UnsupportedProtocolVersionError`时进行相应处理。

#### 步骤四：调用 server/discover（可选）

可在任何其他请求前调用`server/discover`进行版本选择或兼容性探测。

#### 步骤五：适配MRTR

处理服务器返回的`InputRequiredResult`，在重试原请求时附带`inputResponses`提供所需信息。

#### 步骤六：处理订阅变更

适配新的`subscriptions/listen`机制。

### 3.3 迁移策略建议

**Microsoft的AGT团队采用了“双栈迁移”策略**：在过渡窗口期内同时支持2025-11-25和2026-07-28两个版本，逐步完成迁移。

**关键建议**：
1. 先在非生产环境验证
2. 利用12个月废弃窗口期逐步迁移
3. 注意幂等性设计——无状态后重试变得廉价而频繁，应用层需自行处理去重
4. 状态管理责任从协议层转移到应用层，需要自行设计状态存储方案（Redis、数据库或专门的状态服务）


## 四、生态采纳与厂商跟进分析

### 4.1 采纳速度空前

规范发布后**数天内**，基础设施提供商、SDK维护者、云平台和工具供应商就宣布了支持、发布了迁移指南并推出了生产实现。

### 4.2 主要厂商跟进情况

| 厂商/平台 | 跟进情况 |
|-----------|---------|
| **GitHub** | 规范正式发布**前**就已更新MCP Server，移除了Redis-backed会话存储，消除了每次initialize的数据库写入和每次请求的数据库读取 |
| **Cloudflare** | 发布首日即支持，每个请求在全新无状态服务器上运行，无需协议特定的Durable Object |
| **AWS** | 在Amazon Bedrock AgentCore中提供无状态核心，无需管理会话即可在标准可扩展基础设施上部署MCP服务器，并贡献了Tasks扩展 |
| **Vercel** | 7月31日宣布支持新规范，客户端无需任何更改即可获得无状态请求模型 |
| **Supabase** | 其MCP服务器本就是无状态的，新MRTR设计让其工具可以在调用中途暂停并与用户确认 |
| **阿里云/腾讯云/百度云** | MCP广场同步接入新规范，恒生聚源等数据平台在上线首日完成适配 |

### 4.3 行业背景

2026年7月28日这一周被称为Agent协议层的 **“Kubernetes时刻”** 。同一天，A2A协议庆祝一周年并宣布150+组织生产部署；中国发布GB/Z 185-2026《智能体互联互通》国家标准；29国在上海签署WAICO创始文件。

MCP的月度SDK下载量已突破**4亿次**门槛。MCP已从Anthropic发起的项目成长为行业事实标准——OpenAI、Google、Microsoft、AWS等主要AI厂商均原生支持MCP。

### 4.4 趋势判断

MCP此次无状态化重构，本质上是**将状态管理的责任从协议层转移到应用层**——这是一次产业分工的重新划界。云厂商反应最快，因为状态被推到应用层后，托管状态服务就成了一门可以计费的生意。

与此同时，Google在同一周推出了Agent Substrate——定位是Agent时代的统一基础设施层。两者方向相反：MCP把状态管理推出协议层，而Agent Substrate试图在更底层接管它。这意味着Agent基础设施层的竞争才刚刚开始。
