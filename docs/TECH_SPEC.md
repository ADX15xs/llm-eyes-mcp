## 1. 项目概述

**llm-eyes-mcp** 是一个为纯文本大模型（如 DeepSeek）补全视觉能力的 MCP（Model Context Protocol）服务端。

### 1.1 核心定位

一句话定位：**一把 <20MB 的"视觉游标卡尺"**——凭借免费/开源的 VLM 提取坐标，通过 Go 原生数学做硬核计算，依靠三级缓存省钱，依赖意图路由保精度。

### 1.2 三大范式突破（对外宣传聚焦点）

1. **路由逻辑**：让 LLM 做调度，而非看图。将"视觉任务"从"模型黑盒"中抽离，精确的事回归计算，模糊的事回归感知。
2. **成本壁垒**：三级缓存机制使单会话成本降低 70%~90%。
3. **极致轻量**：零 CV 依赖（无 OpenCV），<20MB 单体二进制，`go install` 秒级安装，天然跨平台。

### 1.3 与原生多模态模型的差异化

原生多模态模型（GPT-4o 等）对空间的感知是"概率性的模糊匹配"，而非"确定性的数学计算"。llm-eyes-mcp 定位为原生模型的**精密卡尺插件**：

- **精确性碾压**：VLM 只看坐标（bbox），Go 做算术（`math.Hypot`），返回浮点数 `245.7` 而非"约 250px"。
- **成本颠覆**：同一张图多次提问，缓存直接命中，成本仅为原生模型的 1/10~1/20，响应从秒级降至毫秒级。
- **可解释性**：每一步可审计、可修正，工业级场景刚需。

> 定位总结：**原生多模态模型是"眼睛"，负责感知世界；本 MCP 是"手和尺子"，负责精确改造世界。** 不替代原生模型，而是把原生模型从"主角"降级为"昂贵的传感器"，仅在必要时启用。

## 2. 背景与设计理念

### 2.1 参考对象：ds-vision-skill（作为反面教材）

`ds-vision-skill` 是一个让 DeepSeek 借 GLM-4V-Flash 看图的能力补全工具，本质是"桥梁/中继系统"。其缺陷分析：

| 问题 | 说明 |
| :--- | :--- |
| 信息坍缩 | 空间→文本转换不可逆，DeepSeek 无法做精确视觉推理 |
| 数据冲突 | GLM 语义描述与 MinerU OCR 结果缺乏仲裁机制 |
| 格式强依赖 | 解析逻辑与 API 输出模板强绑定，API 升级即崩溃 |
| 上下文挤占 | 超长描述吞噬窗口，无动态摘要/截断机制 |
| 哈希碰撞隐患 | 缓存键基于文件名，同名覆盖/碰撞返回旧图描述 |
| 网络强依赖 | 稳定性取决于外部 API 与网络 |

### 2.2 理论基础：DeepSeek "视觉原语"（Thinking with Visual Primitives）

DeepSeek 2026 年 4 月发布的论文核心观点：模型不仅要"看见"，更要在推理时能精确"指代"（解决指代鸿沟 Reference Gap）。**点坐标和边界框**才是精确的"最小思维单元"。

- 纯文本描述（"左边那个"）太模糊；坐标（x, y）才是确定性的。
- 实测处理 800×800 分辨率图片仅消耗约 90 Token。
- 将空间推理从"结果"变为"思考过程"的一部分。

**本项目落地方式**：不追求让 LLM 内化视觉原语（需模型权重支持，MCP 无法实现），而是把图像抽象为"坐标锚点 + 标签"的数学描述（几何 DSL），让 DeepSeek 在纯文本域内做空间逻辑推演。

### 2.3 关键认知约束（踩坑总结）

1. **不能做"特征直传"**：外部模型特征向量与 LLM 嵌入空间不对齐，不微调的情况下 DeepSeek 看不懂浮点向量。只能输出文本/结构数据。
2. **DSL 只是"拐杖"**：只能处理几何确定性任务（距离、重叠、计数、OCR 校验），无法解决符号接地问题（"美感""语义突显性"）。
3. **"像素级精确"是伪命题**：无物理标定时，本地 OpenCV 测量的"245.7px"同样是幻觉，精度受制于 VLM 坐标输出质量。
4. **长上下文不是保险箱**：迭代聚焦产生历史坐标冗余，存在"Lost-in-Middle"现象。

## 3. 核心架构设计（V5 - 生产版）

### 3.1 设计原则

- **不依赖 LLM 意图猜测**：意图路由由 Agent 的 Tool Calling 机制完成，MCP 只接收确定性指令。
- **不修改客户端**：纯 MCP 规范实现，尊重现有 Agent 生态（Claude Desktop、Cursor、Codex 已原生暴露 MCP Tools）。
- **推理与测量物理分离**：LLM 负责"意图路由"和"自然语言润色"，所有"尺子"功能由确定性计算接管。

### 3.2 工具定义（3 个高度聚焦的 Tool）

> 关键：不提供万能的 `analyze_image`，而是拆分多个聚焦工具。**Description 的精准性决定 Agent 选对工具的概率**，缓存按 Tool 名索引。

#### Tool 1: `measure_image`（硬管道入口）

- **Description**：`Execute precise geometric measurement on the image. Use this ONLY when user explicitly asks for distance, size comparison, alignment check, or area calculation. Do NOT use for semantic understanding or style analysis.`
- **输入**：`image_uri`（客户端注入）、`measure_type`（枚举：`distance | alignment | area`）、`target_labels`（如 `["screw_A", "screw_B"]`）
- **输出**：`{"value": 245.7, "unit": "pixels"}`

#### Tool 2: `describe_image`（软管道入口）

- **Description**：`Analyze image for semantic content, artistic style, color harmony, emotional tone, and subject identification. Use this ONLY when user asks about aesthetics, scene understanding, or qualitative attributes.`
- **输入**：`image_uri`、`focus`（枚举：`style | subject | color | emotion`）
- **输出**：自然语言描述（VLM 生成）

#### Tool 3: `extract_text`（OCR 入口）

- **Description**：`Extract and return all human-readable text content from the image via OCR. Use this ONLY when user explicitly asks to read text, numbers, or tables from the image.`
- **输入**：`image_uri`
- **输出**：结构化文本（VLM/OCR 生成）

### 3.3 双管道处理（V2.1 起引入）

| 管道 | 适用问题 | 流程 | 精度 | 成本 |
| :--- | :--- | :--- | :--- | :--- |
| **硬管道** | 测量/验证/计数/对齐 | VLM 粗标坐标(JSON) → Go 原生算术 | 亚像素级（取决于 VLM 坐标质量） | 极低 |
| **软管道** | 风格/鉴赏/主体识别 | 原图直接打包给高性能 VLM 语义理解 | 语义级（非量化） | 中等/高 |

**混合任务**（如"距离 + 色调评价"）：先走硬管道取数值，再走软管道取评语，最后 DeepSeek 融合输出。

### 3.4 处理流程（4 步严控）

1. **Step 1 全局稀疏标注**：轻量级 VLM 仅提取物体标签 + 粗略中心点（限时 500ms），输出如 `[{label:"cup", x:0.4, y:0.5}]`。
2. **Step 2 意图解析与动作选择**：由 Agent 的 Tool Calling 完成（不依赖 DeepSeek 语义分类）。
3. **Step 3 本地硬计算**：Go 对 VLM 输出的归一化坐标执行 `math.Hypot`、IoU、计数等（不经过 LLM）。
4. **Step 4 最终语义合成**：硬数据 + 用户问题喂给 LLM 生成自然语言回答。

### 3.5 迭代收敛控制

- 默认最多 **2 轮**交互，防止 Token 爆炸。
- 每轮进入最终合成时丢弃中间 VLM 长文本，只保留数值和用户原问题，防止"中间丢失"。

## 4. 图片接入与分发（V3.1）

### 4.1 万能图片加载器（Universal Loader）

Agent 传图机制五花八门，MCP 第一道关卡必须兼容所有格式。输入参数统一为 `image_source`（字符串），内部协议嗅探：

| 输入形式 | 处理逻辑 |
| :--- | :--- |
| `http://` / `https://` | `http.Get` 下载（处理跳转与重试） |
| `file://` / `/` 开头 | `os.ReadFile` 本地读取 |
| `data:image/...` | 解析 Base64 前缀并解码 |
| 纯 Base64 | 直接解码 |

加载后立即计算 **MD5** 存入 L0（原始归档），然后丢弃原始字符串释放内存，输出统一内部标识 `image_id`（即 MD5）。

### 4.2 图片注册表（Image Registry）

- 映射：`image_id (MD5) -> 已计算的 VLM 坐标/描述摘要`。
- 流程：首次传图 → MCP 返回 `image_id` 给 Agent 作为引用 → 后续会话携带 `image_id` 提问，无需重新加载原图。
- 意义：Agent 无需记住庞大的 Base64 数据，只需一个短字符串 ID；缓存跨会话复用成为可能。

## 5. 图片预处理规范（V2.2）

### 5.1 智能压缩（感知型，按管道区分，禁止一刀切）

| 管道 | 压缩策略 | 目的 |
| :--- | :--- | :--- |
| **硬管道**（测量/OCR） | 保持长宽比，最长边 ≤ 1500px，**无损 WebP/PNG**，禁止 JPEG（振铃效应破坏边缘） | 保留亚像素级边缘 |
| **软管道**（风格/鉴赏） | 激进压缩至 512px，高质量 JPEG（质量 85%） | 低频语义信息低分辨率可识别，体积 < 50KB |
| **混合任务** | 分别压缩两次，各走各的管道 | 术业有专攻 |

**原理**：VLM（ViT 架构）内部自带分块器（Patch Embedding，如 14×14）。超高清图会切出数万 Patch，注意力被稀释反而降低精度；无损下采样到原生训练分辨率附近，OCR 与主体检测准确率反升 5%~10%。

### 5.2 图像增强（优先级高于压缩）

- **CLAHE（对比度受限自适应直方图均衡）**：模糊文档照片 OCR 准确率提升显著。
- **锐化掩膜（Unsharp Masking）**：工业零件图边界框定位更准。

### 5.3 规范原文（写入设计文档）

> **MCP 图片输入预处理规范**：若意图为 `HARD_MEASURE`，执行无损缩放至长边 1500px；若意图为 `SOFT_PERCEPTION`，执行有损缩放至短边 512px；所有图片传入 VLM 前，强制执行 CLAHE 对比度增强。

## 6. 缓存架构（V3.1 修正版）

### 6.1 核心原则

- **意图先行，原始存档，按需加工**：拿到意图前绝不做任何不可逆的图片变换。
- **缓存键必须包含 Tool 名（而非意图文本）**：`{MD5}_{TOOL_NAME}_{PARAM_HASH}`，消除同图不同措辞导致的缓存失效。

### 6.2 四级缓存体系

| 层级 | 命名空间 | 存储内容 | 缓存键示例 | 命中场景 | 介质 | TTL |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **L0 原始归档** | `raw:` | 原始二进制流（零变换） | `raw:{MD5}` | 防止重复上传 | 本地磁盘 | 不删（配额保护） |
| **L1 加工成品** | `proc:` | 按意图处理后的图片流 | `proc:{MD5}_{INTENT}_{SCHEMA_VER}` | 硬/软管道各自复用 | 磁盘 | 24h |
| **L2 VLM 语义/粗标** | `vlm:` | VLM 返回的 JSON/文本 | `vlm:{MD5}_{TOOL_NAME}_{MODEL_VER}` | 同图同 Tool 复用 | SQLite | 静态图 7 天 / 实时截图 10 分钟 |
| **L3 几何硬算值** | `geo:` | OpenCV/Go 计算的浮点值 | `geo:{MD5}_{ACTION}_{PARAMS_SORTED}` | 同图同参数重复测量 | 内存 LRU（≤1000 条） | 会话有效 |

### 6.3 缓存键硬规则（避坑指南）

1. **必须基于图像内容 MD5**，而非文件名/URL（同名覆盖会返回旧图描述）。
2. **混合任务分拆缓存**：硬管道产出数字、软管道产出评语，分别缓存，合成时即时拼接。
3. **必须包含模型版本**：`GLM-4V-Flash-0902` 与 `1010` 对同图输出可能不同。
4. **必须包含 Schema 版本**（`CACHE_SCHEMA_VERSION`）：调整压缩逻辑时递增版本号，旧缓存自然失效。
5. **L1 与 L0 解耦**：MD5 标识原始数据，Intent/Tool 标识处理参数，杜绝"不同处理方式共用同一 MD5"的误命中。

### 6.4 失效与配额

| 项 | 值 |
| :--- | :--- |
| L1 磁盘上限 | 1GB，超限按 LRU 淘汰 |
| L2 数据库上限 | 100MB |
| 启动巡检 | 自动清理 L1 超过 48h 未访问的图片 |
| 强制刷新 | 用户表达"重新识别"意图时强制跳过 L2，直调 VLM 并回写 |
| 清空时机 | 切换 VLM API Key 时自动清空 L2 |

### 6.5 缓存优先流程

1. 计算 MD5 → 查 L0（命中取原图，跳过重复上传）。
2. Agent 调用 Tool → MCP 以 `{MD5}_{TOOL_NAME}_{PARAM}` 查 L2。
   - 命中：零 API 调用、零网络延迟。
   - 未命中：调 VLM，写入 L2，喂给下游。
3. 仅硬管道查 L3：命中跳过重计算，未命中执行后写入。

## 7. 技术栈（V3.0 决策）

### 7.1 关键决策：砍掉 OpenCV

- **背景**：GoCV（Go 绑定的 OpenCV）编译后约 500MB，对追求传播率的开源 MCP 是致命缺陷（下载慢、CGO 依赖冲突、劝退用户）。
- **替代方案**：**VLM 直出坐标 + Go 原生算术**。现代 VLM 归一化边界框误差通常 1%~3%，对通用场景完全够用；未标定照片的本地"亚像素测量"本质也是伪精度。

### 7.2 技术栈清单

| 组件 | 方案 | 体积 | 说明 |
| :--- | :--- | :--- | :--- |
| 语言 | Go | - | 纯标准库 |
| 图片压缩/格式转换 | `image/jpeg` + `golang.org/x/image` | ~0MB | 标准库 |
| HTTP 客户端 | `net/http` | ~0MB | 调 VLM API |
| JSON 解析 | `encoding/json` | ~0MB | 解析坐标 |
| 几何计算 | `math`（`math.Hypot` 等） | ~0MB | 距离/面积/交集 |
| SQLite | `modernc.org/sqlite`（纯 Go） | ~6MB | 无 CGO |
| **最终二进制** | `go build` | **< 20MB** | 单文件分发 |

### 7.3 模型无关性

架构完全依赖"结构化文本/代码逻辑"通信，不依赖任何专有 API 参数，**适用于所有纯文本大模型**（GPT-4o、Claude、Gemini、Qwen2.5 等）。切换模型仅需更换 API Base/Key 并微调 System Prompt 措辞。DeepSeek 的加分项：1M 上下文、代码/数学性价比高、与视觉原语论文同源。

## 9. 能力边界（务必写入 System Prompt）

**System Prompt 第一行建议**："本工具专供几何测量与结构布局验证，不负责图像鉴赏。"

### 9.1 最擅长的图片类型

1. **人造刚性物体**：PCB 电路板、机械零部件、建筑平面图、UI 截图、货架商品——边缘清晰、几何约束强。
2. **高密度表格与票据**：财务报表、体检报告、发票——坐标映射任务，规避 LLM 幻觉填数。
3. **前后对比图**：缺陷对比、卫星图变化检测、UI 改版对比——VLM 找变化区域，计算像素差异百分比。

### 9.2 最匹配的任务场景

1. **精确空间测量**："离多远？""差多少？"（返回浮点数而非"很近"）。
2. **布局合规性验证**："是否居中？""是否越界？"（计算中心点偏差、IoU，返回布尔/百分比）——适合 UI 自动化测试、印刷品质检。
3. **多源数据仲裁**："以实物为准"（OCR 高置信度 vs VLM 低置信度，交给 LLM 依据证据强弱做决策）——会计审核、单据录入。

### 9.3 明确禁区（架构不擅长）

1. **主观审美与情感分析**：坐标系里没有"忧郁"的数学定义。
2. **无清晰边界的自然场景**：VLM 粗定位易漏标，无法在杂乱纹理中切出实例。
3. **依赖 3D 透视与深度推理**：单目 2D 图片无法用欧氏距离换算，需深度估计模型。

## 10. 竞品对比与优势（精简版）

### 10.1 竞品分类

| 类型 | 代表 | 本质 |
| :--- | :--- | :--- |
| 通用"翻译官"型 | image_mcp、luma-mcp 等 | API 套壳，图片→文字描述 |
| 专用"工具"型 | image-diff-mcp、UI 识别类 | 单一垂直场景 |
| "模型聚合"型 | vision-analyzer | 多 VLM 切换的"多模型翻译官" |
| "局部放大"型 | image-tiler-mcp | 大图切片防细节丢失，非架构革新 |

### 10.2 真正的 3 个核心优势（剔除强行解释后）

1. **意图驱动双管道分流**：用"路由"替代"猜测"，精确的事回归计算，模糊的事回归感知。
2. **三级缓存的成本护城河**：单会话成本降 70%~90%，按 Token 收费场景下是碾压级商业优势。
3. **极致部署轻量**：<20MB 单体二进制、`go install` 秒装、零 CGO、天然跨平台。

> **需要剔除的"强行解释"**：①"双管道专业分工"（是意图路由的必然结果）；②"像素级精确"（无物理标定时是伪命题，只能称"比纯靠 VLM 瞎编更可靠"）；③"解决上下文挤占"（VLM 输出压缩 JSON 后本就不严重）。

## 11. 对原生多模态模型的意义

即使主干 LLM 切换为原生多模态模型（GPT-4o），本 MCP 依然可作为 **Tool 挂载**，填补其两个致命弱点：

1. **物理精度缺陷**：原生模型问"中心距多少像素"会猜"约 150px"；MCP 强制 VLM 输出坐标 + Go 计算，返回 `245.7px`。这是数学，不是猜测。
2. **成本防火墙**：同一张图 10 个问题，原生模型编码 10 次；MCP 缓存让图片只编码一次。
3. **确定性工具接口**：为高精度 RPA、GUI 自动化代理提供稳定的 `get_bbox(button)` 接口，替代原生模型 10~20px 的坐标漂移。

工作流演进：GPT-4o 理解意图 → 主动调用 MCP 的 `measure_distance` → MCP 精算回传 → GPT-4o 润色语言。

## 13. 遗留问题与演进方向

1. **绝对尺寸测量**：若需"螺丝钉实际多少毫米"，需标定板 + 专用测量工具（可作为独立微服务，不编译进主 MCP）。
2. **软管道失败降级**：VLM API 超时自动降级为"抱歉无法分析艺术风格，但可测量几何数据"。
3. **VLM 坐标质量监控**：无物理标定时精度上限取决于 VLM 坐标输出，可考虑多 VLM 交叉验证。
4. **强制触发场景**：若未来 Agent 生态需要"图片进来即预处理"，需客户端配合（当前不做，尊重 MCP 规范）。
